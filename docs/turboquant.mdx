title: TurboQuant
---

TurboQuant is Ollama's compressed KV-cache path for the new engine. It reduces KV memory growth during long-context generation without changing the model's GGUF weight quantization.

## Stable Default Lane

In this checkout, the stable TurboQuant lane is:

- structured WHT/Hadamard-style rotation
- scalar Lloyd-Max / MSE-style quantization
- QJL off by default on both K and V for new encodes
- FP32 V-side reconstruction on every supported path

TurboQuant is KV-cache compression only. Experimental weight-quantization metadata exists separately and does not currently apply active model-weight compression.

## Status

This branch currently exposes:

- `reference_wrapper`: the paper-faithful codec and Go-side wrapper cache path
- `native_backend`: the native-engine migration lane, with explicit guards and status reporting
- `experimental` lanes: segmented `head_dim=576`, K-side QJL, residual FP16 tail, and surface-aware policy handling
- `scaffold-only` lane: experimental weight quantization metadata with `experimental_weight_quant_active=false`

Wrapper-mode runs remain the reference lane. Do not treat them as proof of backend-native KV memory savings until the backend owns the packed KV payload directly.

## Fully Supported vs Experimental

Fully supported in this checkout:

- stable `tq35` / `tq25` request handling with QJL off by default
- FP32 V reconstruction on supported paths
- runtime requested vs effective K/V metadata
- sparse KLD, NIAH, corruption classification, and residual-tail reporting in the benchmark harness

Experimental:

- K-side QJL via `turboquant_qjl_k=true`
- segmented `head_dim=576` via `turboquant_allow_segmented_heads=true`
- residual FP16 tail via `turboquant_residual_tail_tokens`
- surface-aware policy reporting and conservative whole-model fallback for hybrid/SWA models

Blocked or scaffold-only:

- `turboquant_qjl_v=true` is blocked and reported as fallback
- experimental weight quantization is metadata-only and remains inactive
- arbitrary non-power-of-two head dimensions are not enabled beyond `576 -> 256+256+64`

## Rollout Presets

This branch does not recommend one universal TurboQuant mode. Use the support tier and runtime metadata to pick a rollout lane:

- `safe`: recommend symmetric `tq35/tq35` on the primary validated architecture families and `support_tier=safe`
- `conservative`: recommend asymmetric pairings only where the runtime still reports the requested effective K/V path with no fallback
- `experimental`: segmented heads, K-side QJL, residual tails, and hybrid/native rollout work remain guarded

Current conservative guidance is intentionally narrow. Some asymmetric pairings still fail production-style correctness checks, so pairings outside the validated set should be treated as experimental even if they run.

## How To Use It

### One run

Use the recommended mode:

```shell
ollama run gemma3 --turboquant
```

Choose a specific TurboQuant preset:

```shell
ollama run gemma3 --turboquant=tq35
ollama run gemma3 --turboquant=tq25
```

Disable it explicitly for one run:

```shell
ollama run gemma3 --turboquant=off
```

### API

Set `options.kv_cache_type` on `/api/generate` or `/api/chat`:

```json
{
  "model": "gemma3",
  "prompt": "Explain TurboQuant.",
  "options": {
    "kv_cache_type": "tq35"
  }
}
```

Asymmetric overrides are also supported:

```json
{
  "model": "gemma3",
  "prompt": "Explain TurboQuant.",
  "options": {
    "kv_cache_type_k": "q8_0",
    "kv_cache_type_v": "tq35"
  }
}
```

Experimental K-side QJL:

```json
{
  "model": "gemma3",
  "prompt": "Explain TurboQuant.",
  "options": {
    "kv_cache_type": "tq35",
    "turboquant_qjl_k": true
  }
}
```

Experimental residual tail:

```json
{
  "model": "gemma3",
  "prompt": "Explain TurboQuant.",
  "options": {
    "kv_cache_type": "tq35",
    "turboquant_residual_tail_tokens": 128
  }
}
```

### Modelfile default

To make a selected model default to TurboQuant:

```text
FROM gemma3
PARAMETER kv_cache_type tq35
```

More aggressive compression:

```text
PARAMETER kv_cache_type tq25
```

Inspect the stored default with:

```shell
ollama show --parameters your-model
```

### Environment fallback

If neither the request nor the model specifies a KV mode, Ollama falls back to `OLLAMA_KV_CACHE_TYPE`.

`OLLAMA_KV_CACHE_TYPE_K` and `OLLAMA_KV_CACHE_TYPE_V` can override the K or V side independently.

`OLLAMA_TURBOQUANT_PRESET` can be set to `safe`, `conservative`, or `experimental` to drive rollout guidance and warnings without changing the actual requested K/V types.

`OLLAMA_TURBOQUANT_QJL_K`, `OLLAMA_TURBOQUANT_QJL_V`, `OLLAMA_TURBOQUANT_RESIDUAL_TAIL_TOKENS`, `OLLAMA_TURBOQUANT_ALLOW_SEGMENTED_HEADS`, and `OLLAMA_TURBOQUANT_SURFACE_POLICY` control the experimental request-time lane.

## Compatibility And Limitations

- TurboQuant applies to generation and chat paths only.
- The legacy llama runner still rejects TurboQuant modes.
- TurboQuant modes require the new engine path.
- Quantized KV modes may require Flash Attention support depending on the effective K/V pairing.
- `reference_wrapper` remains the stable comparison lane for this branch.
- `turboquant_qjl_v` is blocked in this checkout and is never silently enabled.
- Hybrid/SWA architectures currently report surface-aware metadata and use conservative whole-model fallback when per-surface dispatch is unavailable.
- Segmented `head_dim=576` support is experimental and opt-in only.
- Experimental weight quantization remains scaffold-only metadata in this checkout.
- `native_grouped_scaffold` and `native_backend` should not be assumed wire-compatible across distributed or RPC boundaries unless both ends match layout kind, layout version, and path semantics.

## TurboQuant And GGUF Quants

TurboQuant is KV-cache compression. It does not replace the model's GGUF weight quantization.

That means you can use TurboQuant on top of the GGUF model-weight formats that Ollama already loads successfully through the new engine, for example:

- `F16`
- `Q8_0`
- `Q6_K`
- `Q5_K_M`
- `Q5_K_S`
- `Q4_K_M`
- `Q4_K_S`

This is not a separate closed compatibility matrix. TurboQuant overlays the normal GGUF model-weight format you already use.

## Benchmarks

Use the benchmark tools in:

- `scripts/benchmark_turboquant_plan5.ps1`
- `scripts/benchmark_turboquant.ps1`
- `cmd/bench`
- `cmd/benchkv`
- `cmd/benchppl`

Recommended comparison set:

- baseline: `f16`, `q8_0`, `q4_0`
- TurboQuant: `tq35`, `tq25`
- experimental: K-side QJL on/off, residual-tail `0` vs `128`

Suggested metrics:

- peak KV memory
- total process memory
- first-token latency
- steady-state tokens/sec
- perplexity
- sparse KLD vs baseline where available
- NIAH retrieval pass/fail
- corruption class / empty-output / truncation detection

Token-match can still be useful as a secondary proxy, but it is not the primary acceptance criterion for this branch.
